# ADR 0005：业务持久化、账号隔离与数值口径

## 状态

已实施并接受（2026-10-10）。本地回归及真实云端浏览器验收见 [验收报告](../reviews/2026-10-10-unified-fixes-e2e.md)。

基于 `main@c922ded`，工作分支 `codex/unified-report-fixes`。
问题证据与复测边界见 [当前 main 测试报告复核](../reviews/2026-10-09-main-report-review.md)。

## 目标

把现有流程接成「邮箱密码登录 → 当前用户业务 API → Supabase PostgreSQL → 服务端恢复与派生结果」闭环。
优先消除账号数据串用和假保存，再修正菜谱选择、盘数、认证响应及数值一致性。
沿用 ADR 0001 的 FastAPI 单体和 ADR 0002 的六张业务表；保持邮箱密码 MVP 范围。

## 统一设计

### 1. 服务端是业务数据源

营养基线、菜谱和周计划的已保存状态以服务端为准，前端只保留当前用户的页面状态与未提交草稿。
正式登录流程不再从 `meal-prep-planner-demo-v1` 读取业务数据，不自动注入演示菜谱或默认已确认目标。
现有全局缓存没有可靠所有者，禁止自动归属给接下来登录的账号或上传到其数据库；保留旧 key 供人工核对，本应用停止读写它。
若保留页面偏好缓存，仅存非业务偏好，key 同时包含项目标识、用户 ID 和版本。

认证层向业务层提供统一初始化入口和会话变化通知，覆盖初始会话恢复、登录、退出、切换账号和 token 刷新。
用户变化/退出时同步清空内存状态、派生结果、编辑器和页面 DOM，再加载新账号；不能只隐藏旧页面。
取消旧请求，并以账号代次校验异步结果；当前周变化也应阻止上一周响应覆盖新视图。
同账号 token 刷新更新凭据即可，不能重复初始化或丢弃草稿。处理 SDK 回调与初次会话读取的重复事件。

加载期间禁用业务保存；读取失败显示错误和重试，不恢复演示数据。请求成功后以服务端返回值更新页面并显示保存成功。
网络失败保留当前账号草稿，但不宣称已保存。写请求超时会提示先重新读取确认保存结果，应用不自动重试写入。
`/health` 仅代表进程存活，不能单凭它显示“数据随时保存”；持久化就绪状态应独立检测。

### 2. 保留业务 API，补充统一请求与映射层

新建前端业务 API 模块，所有业务请求在发起时取得当前 access token，携带 `Authorization: Bearer ...`。
统一处理 JSON/204 响应、401、404、409、422 和服务不可用；错误不降级为本地成功。
登录后加载食材目录、基线、菜谱和当前周计划，再读取周营养与采购清单。切周只读，不因渲染自动创建计划。
基线未确认/计划不存在的 404 显示对应空状态，不能把所有错误都当空数据。

| 页面动作 | 现有 API | 适配要求 |
| --- | --- | --- |
| 读取食材 | `GET /api/v1/ingredients` | 使用真实 bigint ID；分类代码由 UI 翻译，不按位置映射旧标识 |
| 计算/确认/恢复基线 | `POST /nutrition/calculate`、`PUT/GET /profile/baseline`（均在 `/api/v1`） | 保存身体输入和确认目标；仅有计算结果不等于已确认基线 |
| 新建/编辑/归档/列表 | `/api/v1/recipes` 及 `/{recipe_id}` | 用服务器 UUID 和返回的营养值；空列表保留为空 |
| 建立/读取周计划 | `POST /api/v1/meal-plans`、`GET /api/v1/meal-plans/{week_start}` | 按周一日期索引；首次真正保存餐项时创建；重复周 409 后重读 |
| 添加/替换餐项 | `POST/PUT /api/v1/meal-plans/{week_start}/items` | 明确 `input_mode`；处理日期、数量及排序；替换时保留未编辑的人工餐/其他餐项 |
| 周营养/采购 | `GET /api/v1/meal-plans/{week_start}/nutrition`、`/shopping-list` | 服务端结果作为已保存计划的展示依据 |

前端状态映射统一处理 `week_start`、目标 `kcal`/`target_kcal`、人工餐响应的 `manual_nutrition` 与提交的 `manual_*`。
新计划使用当前已确认目标快照；读取旧计划时展示它自己的快照，禁止 `currentPlan()` 以当前基线覆写。
菜谱归档应排除新建餐项选择，但保留已存在计划的历史可读性；停用食材不应导致历史明细无法计算。

### 3. 后端采用请求范围的 Supabase 仓储

先抽取仓储接口，把各服务的 `MemoryRepository` 类型依赖改为协议，并将路由改为显式依赖注入。
增加按请求绑定已验证用户与 access token 的 Supabase 仓储，普通读写使用已有 httpx 访问 Data API，沿用公开 key 和用户 JWT，让数据库 RLS 生效。
不得在全局单例客户端上修改用户凭据。不要使用 service_role 处理普通用户业务请求，也不信任请求体中的所有者字段。
内存仓储仅通过测试依赖替换启用；正式持久化模式缺少配置/数据库不可用时明确失败。
该模式下缺少 Auth 配置返回 503，失效凭据返回 401，不能把任意 Bearer 当用户 ID。

不能仅替换 `get_repository()`：计划添加和整组替换必须调用明确的持久化方法，不再通过修改返回对象模拟写入。
目录、Profile、菜谱/明细、周计划/餐项都要完成字段映射；数值使用 Decimal，日期/时间/UUID 显式转换。
将 API 校验范围与现有数据库约束对齐（例如人工餐名称长度、目标字段位数），优先收紧校验而非扩大业务表。
区分唯一周冲突、输入/约束错误、无访问权或不存在、上游超时；不向客户端返回 SQL 或凭据详情。

### 4. 多表写入通过数据库事务完成

数据库已有“菜谱必须非空”的延迟约束：单独 POST 菜谱父记录、再 POST 食材的两次 REST 请求无法保证成功。
新增最少量的 `SECURITY INVOKER` RPC：菜谱创建/整体更新，以及周计划餐项的原子替换。
每次调用内部完成校验和多表操作，失败时整体回滚；普通单表读写继续走 Data API。
函数依据 `auth.uid()` 和父记录所有权校验访问，不接受调用方任意指定用户；设置明确 search_path，并只对所需角色授权。
保留 RLS、跨表所有权和日期约束，不为绕过错误放宽策略。

同一计划的修改在事务内锁定父记录。为整组替换增加旧状态校验（使用父计划 `updated_at` 作为 `expected_revision`），不一致返回 409 并要求重新加载，避免跨页面/设备静默覆盖。
新增餐项提交期间禁用重复操作；创建周计划的竞争交给现有唯一约束处理。

此处新增 RPC 是满足现有多表事务约束的集成设施，不是新业务表。先在本地验证，记录精确变更并生成迁移；不能用重跑整个 `schema.sql` 代替升级已有库。
方案阶段未部署云端 SQL。实施时用户明确授权将 `business.sql` 部署至测试项目 `meal_plan`，远程迁移版本为 `20261009150703`。

### 5. 一次汇总后舍入，盘数单独定义

统一计算规则：每种食材每 100g 生重营养 × 单盘生重 ÷ 100 × 盘数，保留中间精度，再在需要展示的单盘、餐项、日或周层级各自最终舍入到一位小数。
周结果从原始明细直接累计，不能由已经舍入的单盘、餐项或每日结果累加。后端采用 Decimal + `ROUND_HALF_UP`；数据库使用等价的 numeric 最终舍入。
Profile 目标在确认/存储时按一位小数量化，读取和计划快照沿用已确认数值，避免落库后与内存响应产生不同舍入结果。
前端已保存结果直接显示服务端值；未提交草稿预览与权威结果区分，预览逻辑也去掉逐菜谱中间舍入。

数据库现有视图中已确认有中间舍入路径，需纳入修复：日/周汇总改从未舍入明细聚合，保留公开展示列的一位小数契约。
迁移需处理视图依赖，不直接用 `CREATE OR REPLACE VIEW` 改变已有列类型。可在各汇总查询内部使用原始明细 CTE，避免先使用单盘展示视图的已舍入数值。
现有每 100g 两位小数、生重一位小数、数量两位小数足以表达本次样例；目前没有扩展表数值精度的依据。

“盘数”定义为 `input_mode = recipe` 的 `quantity` 总和，支持小数盘；人工餐不计入盘数。
“餐项数”是记录条数，“餐次数”是不同日期和餐次组合数；标签与计算分别对应，不能混用。
周计划摘要和采购摘要采用同一盘数函数。午餐 2 盘、晚餐 1 盘应均显示 3 盘。

点击“加入本周计划”时把按钮的 `recipe_id` 放入待新增餐项，由编辑器显式选中；常规“添加餐项”可采用默认值。
校验所选菜谱仍有效，不因列表排序、新增菜谱或重新加载改变用户选中项。

### 6. 修复认证契约并正式加载启动配置

后端 session 解析同时支持顶层 REST token 响应和兼容的嵌套 session；合法注册待确认响应允许没有 session。
出现 token 字段但缺少必需 token 时返回上游契约错误，不能伪装成无会话注册成功。
分别覆盖注册、登录、刷新、无会话、缺字段、错误响应；使用合成官方响应，无需创建真实账号完成单测。

后端启动读取显式指定的环境文件；提供仅含公开 URL/key 的运行时配置脚本，`index.html` 在 `auth.js` 前加载。
该脚本使用规范 JSON 序列化、禁止缓存过期配置，不输出其他环境变量；私密数据库配置、secret/service_role key 不进入响应。
补充正常启动命令、持久化模式与测试模式说明，不再依赖报告目录中的 `configured_preview.py`。
修正 README 的验证码描述、`AGENT.md` 的过时架构说明，保持邮箱密码 MVP 决策一致。

## 实施顺序与交付

以下是同一修复分支上的顺序阶段；每阶段完成对应回归，不在中间阶段宣称完整 E2E 已通过。

| 阶段 | 主要文件/改动 | 完成条件 |
| --- | --- | --- |
| 1：隔离与认证基础 | `frontend/auth.js`、`frontend/app.js`、统一 API/会话模块；`services/auth.py` 及认证测试 | 切账号立即清空页面与草稿；旧请求不能回填；不再读全局业务缓存；三个 REST session 契约通过 |
| 2：数据库仓储与事务 | 仓储协议/Supabase 适配器、路由依赖、计划服务显式写入、RPC/迁移、数据库测试 | 基线、菜谱、计划实际写库并可重读；多表失败无部分数据；A/B 越权拒绝；内存模式不隐式降级 |
| 3：完整页面接 API | 基线/菜谱/周计划/采购的状态映射及加载流程 | 清空当前测试站点业务缓存或在独立 origin 登录后恢复；重启服务后仍恢复；失败不显示保存成功 |
| 4：业务细节与一致精度 | 菜谱选择、盘数函数、原始精度计算/SQL 视图、快照与跨月边界 | 新增菜谱不干扰选中项；3 盘正确；四项营养跨层一致；旧周快照不随基线变化；跨月添加成功 |
| 5：正常启动与完整验收 | runtime 配置、README/项目说明、接口与浏览器 E2E | 正常启动无需临时适配器；375px 可用；完整 A/B 与恢复场景通过；形成新验收报告 |

## 验收矩阵

| 范围 | 必须新增/更新的有效回归 |
| --- | --- |
| 账号隔离 | A 保存后退出登录 B；B 不见 A 的任何目标/菜谱/计划/采购结果；A 延迟响应在 B 登录后返回也不得渲染 |
| 会话事件 | 首次恢复只初始化一次；同账号刷新 token 不清空草稿；跨标签页退出清空状态；未登录不能操作业务 |
| 持久化闭环 | 浏览器操作 → HTTP 成功 → 对应用户数据库记录可查；重启后端、独立 origin/浏览器登录 A 恢复相同数据 |
| 权限 | A/B 从 FastAPI 与数据库角色路径交叉读写均不能访问对方记录；伪造 user_id、父记录 ID、recipe_id 无效 |
| 原子性与竞争 | 无效食材/餐项使整笔回滚；创建菜谱不得留下空父记录；重复周 409；旧版本整体替换不能覆盖新餐项 |
| 菜谱选择 | 至少两道菜谱；新增一道置顶后点击原有三文鱼，编辑器仍选中三文鱼，提交/重读保持 ID |
| 数量与精度 | 2+1 盘显示 3；0.5 盘累计正确；人工餐不计盘数/采购，但计入营养；覆盖半舍入边界与多日汇总 |
| 数值基准 | 无人工餐样例三盘：935.1kcal、蛋白质 121.7g、碳水 25.8g、脂肪 38.6g；前端最终展示/API/数据库最终周值一致 |
| 计划稳定性 | 确认新基线不改旧周快照；切周不自动创建空计划；2026-09-28 所在跨月周及跨年周正常添加 |
| 故障行为 | 缺配置、过期凭据、API/数据库故障、写超时均明确反馈；不写入全局缓存、不回退到内存“保存成功” |
| 正常启动 | 公开运行配置在认证初始化前可用；响应中无私密 key/环境信息；健康状态不冒充持久化成功 |
| 浏览器体验 | 375px 登录/注册、错误提示、菜谱编辑和周计划无横向溢出；真实密码登录、退出与会话恢复 |

更新 API 时按项目规则同步补后端测试；既有 74 项回归仍需通过，新测试必须覆盖上述真实失败路径，而不只校验 mock 返回。
默认 pytest 只收集后端，完整验收要显式运行 `backend/tests supabase/tests`、前端测试、数据库数值/事务对照及业务 E2E。
云端验证使用明确测试环境中的专用账号和唯一运行标识，记录精确 ID；退出并核对会话后仅清理该次测试账号及级联数据，最后复查计数。
独立 origin 能证明不依赖相同 localStorage；实际跨设备验收需另行执行，不能把两者混为一谈。

仓库依据：[ADR 0001](0001-mvp-architecture.md)、[ADR 0002](0002-database-design-open-questions.md)、[ADR 0004](0004-email-password-mvp.md)。

已核对 [Supabase 更新日志](https://supabase.com/changelog)，以及以下官方接口/安全文档：

* [Auth OpenAPI](https://github.com/supabase/auth/blob/master/openapi.yaml)：原始 token 响应契约。
* [Data API 访问控制](https://supabase.com/docs/guides/api/securing-your-api)：对象 grants 与行级 RLS 是不同层级，接通时都需验证。
* [数据库函数](https://supabase.com/docs/guides/database/functions)：函数权限和 invoker 方式；本方案在此基础上提出事务 RPC。
